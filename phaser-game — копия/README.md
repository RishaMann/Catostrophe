# Sad Little Cat — Phaser/TS клиент

Новая реализация по `Documentation/Промпт_разработки_двойная_сетка.md` (Phaser 3 + TypeScript, двойная сетка: квадраты для расстановки, гексагоны для навигации кота). Старый прототип (`../index.html` + `../app.js`) не трогается и продолжает жить отдельно.

## Запуск

Нужен Node.js (LTS, 18+). Установить: https://nodejs.org, либо `winget install OpenJS.NodeJS.LTS`.

```bash
npm install
npm run dev
```

Откроется адрес из вывода Vite (обычно http://localhost:5173).

## Тесты

```bash
npm run test
```

`src/iso/hexLattice.test.ts` — технический тест решётки (8×8): размер/отсутствие
дублей, дыры в мощении, границы, `at()`/`fromScreen()`/`fromWorld()`, площадь
гекса против квадратной клетки. **Важно:** тест фиксирует найденное
расхождение со спецификацией — см. раздел ниже.

## Статус (см. §12 промпта — план из 8 шагов)

- [x] Шаг 1 — `projection.ts` + пустая комната (пол, две стены, сетка стен).
- [x] Шаг 2 — квадратная сетка + мебель кубами, якорные правила при ресайзе (`?w=&d=` в URL — временно, до debug-слайдера из шага 8).
- [x] Шаг 3 — гекс-решётка навигации + debug-слой 2 (контуры).
- [x] Шаг 4 — мост между сетками (`latticeBridge.ts`), debug-слой 3 (заливка заблокированных).
- [x] Шаг 5 — A* (`nav/astar.ts`).
- [x] Шаг 6 — ходьба кота (тап по полу) + ракурсы (`cat/CatAgent.ts`). Визуал — настоящий спрайт (см. «Арт кота» ниже), плейсхолдер (кружок+клин) убран.
- [x] Шаг 7 — сортировка по глубине/перекрытие (`iso/depth.ts`, `depthOf()`); мебель и кот теперь рисуются вместе, пересортировкой каждый кадр.
- [x] Настройки сцены (панель) — перенос функционала старого `app.js`
  (`params`/`SLIDERS`/тумблеры `tg[]`). В старом прототипе это была
  design-time панель (`?mode=design`), скрытая от игрока в обычном режиме —
  здесь по той же причине это часть debug-инструмента (`debug/DebugGridScene.ts`),
  а не игровое UI: шестерёнка в правом верхнем углу при `?debug=1`
  (или клавиша `S`) открывает панель со слайдером размера пола (5–10 клеток,
  применяется по отпусканию — не пересобирает патч на каждый пиксель
  перетаскивания), слайдером зума (честный `camera.setZoom`, не трогает
  зафиксированную проекцию — «наклон сцены» из старого прототипа не
  переносился, там это был параметр самой проекции, здесь она зафиксирована,
  §3), тумблерами «кот в комнате» и «проходимость» (заливка гексов —
  зелёным то, что реально достижимо BFS-ом от текущей клетки кота, амбером —
  свободные, но недостижимые «карманы»), и кнопками «Сброс» (вернуть мебель
  к якорным позициям по умолчанию), «Очистить» (убрать всю мебель) и
  «Экран» (fullscreen). Смена размера пола/очистка/сброс всегда безопасно
  переставляют кота на ближайшую свободную клетку новой решётки, если старая
  клетка перестала существовать или оказалась заблокирована.
- [x] Шаг 8 — три режима отображения:
  - обычный (§9.1) — на полу ничего, только круговая волна 200мс на тап;
  - расстановка (§9.2, `room/placementMode.ts`) — тап по стоящему предмету «берёт его в руку» (временная замена входа из магазина/инвентаря), подсветка легальных слотов, красная рамка у слотов, ломающих связность пола, снап призрака, `Esc`/тап без снапа — отмена;
  - debug (§9.3, `debug/DebugGridScene.ts`) — 8 независимых слоёв (клавиши 1–8, `0` — всё выключить), состояние в `localStorage`, текстовая панель (FPS/гексы/путь/изломы/режим), сцена целиком вырезается из prod-бандла (`import.meta.env.DEV` + динамический импорт — проверено сборкой, в `dist/` не остаётся ни строчки реализации).

Активация debug: `?debug=1` в URL. («Четыре тапа по счётчику валюты» из документа не реализованы — в прототипе нет HUD/валюты.)

Каждый шаг проверяется глазами перед переходом к следующему — так и планируем продолжать.

## Известное расхождение со спецификацией (найдено тестом решётки)

§5.3 промпта утверждает: «Все шесть рёбер равны по длине в мировой метрике
[...] никаких поправок на диагональ». По факту, при формулах
`hexCenter`/`hexNeighbors`/`unproject` **из того же документа**, скопированных
буквально, это не так:

- 2 «вертикальных» соседа (шаг (0, ±16) на экране) — мировое расстояние `32√2 ≈ 45.25`;
- 4 «диагональных» соседа — мировое расстояние `16√10 ≈ 50.60`.

Отношение ровно `√5⁄2 ≈ 1.118` — не шум округления, а структурное свойство
формул (проверено и независимым пересчётом вне тестового фреймворка). A* по
факту считает эти рёбра равными по стоимости, хотя геометрически они не
равны — на пути с диагональными шагами кот идёт по факту дальше в мировых
единицах, чем «должен» бы по логике «шестиугольник ⇒ все соседи равны».

Ничего не менял по своей инициативе — числа помечены в документе как
«зафиксированные константы», трогать без обсуждения нельзя.

**Решение (принято сознательно):** живём с расхождением как есть, константы
не трогаем. Тест (`hexLattice.test.ts`) фиксирует РЕАЛЬНОЕ поведение (два
разных, но каждый сам по себе стабильный класса рёбер) — так что если кто-то
позже случайно поправит формулы «чтобы было красиво», тест это заметит и
сломается, а не тихо пропустит расхождение с этой договорённостью.

## Арт кота

Источник — `Documentation/Cats/*.png` (два спрайт-листа 2048×2048, «Батон» —
рыжий, «Шило» — сиамский; ключи скина: `baton`/`shilo`, сейчас в игре
активен `baton`). Картинки полностью непрозрачны (шахматка нарисована как
обычные пиксели, не альфа) — нарезаны и превращены в PNG с настоящей альфой
скриптами в `scripts/` (`slice_sheet.py`, нужен Python 3 + `pillow`/`scipy`/`numpy`),
результат лежит в `public/art/cats/<skin>/`.

**Важно про соответствие 6 направлениям.** В исходнике не 6 отдельных углов
ходьбы, а 3: перед-¾ (плюс повторный дубль-сет того же угла, сейчас не
используется), зад-¾, и прямо-в-спину. Прямого кадра «идёт прямо на
зрителя» нет вовсе. Текущее сопоставление (`cat/catSprites.ts`,
`DIR_SPRITES`) — компромисс:

| Направление (`SPRITE_DIRS`) | Кадры | Зеркало |
|---|---|---|
| front-right | walk_frontleft | да |
| toward-viewer | walk_frontleft | нет *(своего кадра нет — ближайшее приближение)* |
| front-left | walk_frontleft | нет |
| back-left | walk_backleft | нет |
| away-from-viewer | walk_away | нет |
| back-right | walk_backleft | да |

Если понадобится честный кадр «на зрителя» — нужен отдельный спрайт-лист,
имеющимися картинками это не закрыть.

Масштаб (`CAT_ART_SCALE` в `RoomScene.ts`, сейчас `0.075`) и скорость смены
кадра ходьбы (`WALK_FRAME_DIST`) подобраны на глаз под текущий размер
комнаты — стоит пересмотреть, если сильно изменится масштаб сцены.

## Навигационный запас от стен и мебели

Жалоба «заходит на стенку, проходит сквозь объекты» — от того, что решётка
из §5 промпта не даёт запаса: критерий включения гекса — «центр внутри
пола» (для навигации) / «центр внутри занятой квадратной клетки» (для
блокировки, §6, `latticeBridge.ts markBlocked`) — без буфера. У кота есть
спрайт с шириной, а не точка, так что на такой клетке впритык он визуально
вылезал за стену/влезал в мебель, хотя формально центр клетки был снаружи.

Это НЕ трогает формулы решётки (§5) или правило блокировки (§6) — те
зафиксированы, менять нельзя (см. «Известное расхождение» выше). Вместо
этого `nav/navPatch.ts` добавляет два фильтра ПОВЕРХ уже готовой решётки,
после `markBlocked`, перед `buildNeighbors`:

- `markWallMargin` — блокирует клетки с `wx < 10` или `wy < 10` (стены есть
  только у `wx=0`/`wy=0`, см. `RoomScene`);
- `markFurnitureMargin` — для каждого предмета с `blocksFloor` расширяет его
  прямоугольник футпринта на 16 мировых единиц по каждой стороне и блокирует
  клетки, чей центр попал в расширенную область (не только в исходную).

Оба подобраны на глаз и проверены: связность пола (`countFreeComponents`/
ручной BFS) после фильтров не ломается на тестовой комнате, кот визуально
не пересекает стены/мебель на всех проверенных позициях (углы у стен, в
упор к каждому предмету, посередине пути A*). Если добавится узкий проход
шириной в одну клетку между двумя предметами или предметом и стеной — эти
константы могут схлопнуть его в 0 клеток; в этом случае уменьшать margin,
а не спецформулы.
